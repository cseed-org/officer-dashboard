# Route authorization matrix

Source-traced P2 application authorization inventory for `sec/app-and-image`. This documents observed enforcement, not a claim that every route has been exercised. Source locations are a working-tree snapshot; the registration column points to `server/internal/api/routes.go`, and handler locations are under `server/internal/`. No credentials or real personal data are included.

## Reading the matrix

- `S`: officer session cookie, or an **allowlisted MCP tool's in-process officer principal**. A service bearer token alone is not an officer session. MCP does not expose every S route: its generated tool catalog is an additional restriction.
- `P`: separate Launchpad portal cookie, never interchangeable with S. `T(scope)`: scoped service bearer token. `M`: MCP OAuth bearer access token. `Public`: no application credential required; a cookie presented voluntarily can still trigger central cookie-write/origin checks.
- Roles rank **leadership > director > officer**. `director+owner` means the central `/api/admin` director floor **and** the independent owner flag. Role/owner/team are not client-supplied permissions.
- “Shared” is deliberate club-wide access, **not** a missing per-officer ownership check: directory, contacts, events, design reads, programs and officer Launchpad management are collaborative. Object checks concern private drafts, receipts, personal settings, portal linkage, workflow state and privileged actions.
- Minimum role is the **effective middleware plus handler** requirement, not a prefix guess. State checks and conditional privilege increases appear in the last column. “TX” means the relevant check is re-read inside the write transaction; absence of TX is not a promise of race-safe revocation.
- Go ServeMux GET registrations also accept HEAD; these implicit HEAD matches are not separate explicit registrations. `/api/.../` is normalized by hygiene middleware. Canonical-path authorization precedes API canonical redirects. The legacy `/api/buildspace` registrations are listed individually; they invoke the same handlers as canonical Launchpad paths.
- Source links use repository-relative locations. Registration rows cover all literal registrations, every member of the dynamic OPTIONS loop, development-only registrations reached through `registerDev`, redirects and the final static/catchall handlers.

## Central enforcement and trust boundaries

1. **Entry chain:** `api/server.go` `Handler`: recovery -> forwarded-host diagnostic -> API hygiene -> per-IP rate limiting -> `withAuth` -> ServeMux -> `wrap`. `wrap` copies the authenticated principal; it does not itself impose a role. `officer`, `director`, `requireLeadership`, and `ownerIn` are distinct checks.
2. **Officer sessions:** `api/session.go` `withAuth`; `auth/auth.go` `RequiredRoleForPath`; `store/users.go` `SessionByHash`. The database query joins the current user and requires an unexpired session and active user. The absolute session age is also capped. `/api/admin` has a director floor; ordinary `/api` requires officer. `/api/health`, `/api/portal`, `/api/ingest`, `/api/agent`, and `/api/orgcal` are exempt from this role floor and rely on the handlers described below. `/auth`, `/oauth`, `/mcp` are not automatically officer-only.
3. **Onboarding and cookie writes:** pending invite onboarding blocks ordinary API access, including privileged API calls. `/api/me/**`, health, portal, and GET/HEAD club settings remain open subject to their own credentials. Cookie-bearing unsafe requests use `originOK`; portal handlers independently enforce it. OAuth consent POST also checks its form origin. Logout also checks origin without a session; redirects are checked after URL normalization.
4. **Portal:** `api/portal.go` `portal(kind)` authenticates the separate session, account active status, age, requested builder/mentor kind and builder archive status. `portalIn` re-reads the live session/account linkage for mutations. `store/launchpad.go` `LaunchpadSessionByHash` joins only active accounts. `loadBuilder` derives person/project from the account, not a submitted person ID; `builderContext.writable` rejects missing onboarding or archived cohort/person/project. `mentorProjects` requires assignment to a live project in an active cohort. Activity-page store queries filter project scope and visibility before history pagination, and response DTOs filter again.
5. **Service tokens:** `api/jobs.go` `authenticateToken` checks the bearer hash, revocation, expiry, required scope, and a currently active director-or-higher creator. It sets the token principal, clearing any officer principal. `orgOfficer` additionally permits a session with an explicit officer-or-higher role; otherwise it loads the token creator and applies onboarding. Calendar-write scope includes calendar reads; read scope never grants writes. Ingest/job APIs still require their specific token even if an officer cookie exists.
6. **MCP:** `api/mcp.go` `mcpAuthenticate`, `mcpHandle`, `mcpCall`: a live grant and active user are required; tools are filtered and checked by catalog minimum role. Paths and argument keys are constrained, portal/non-API tools are rejected at initialization, and path segments cannot contain slashes or dot traversal. The synthetic request traverses `s.inner` (`withAuth` plus the same API handlers), preserving role, onboarding, object and audit rules. MCP bypasses cookie-origin checks only because the principal is package-internal and bearer-authenticated. It still draws on upload/import and grant budgets. Tool visibility/confirmation text is not the sole authorization control.
7. **OAuth:** `api/oauth.go` authorization is explicit officer consent, with a fresh active user and completed onboarding. Public registration creates client metadata, not officer authority. Token exchange validates one-time authorization code, client, PKCE, resource and redirect binding; refresh validates/rotates a live client-bound grant and active user. Replay revokes grants. Public metadata and CORS/preflight do not authorize application data.
8. **Proxies:** `api/proxyhost.go` only diagnoses a forwarded Host mismatch; it is **not** an authorization boundary. `api/ratelimit.go` trusts forwarded client-IP hops only from configured `TRUSTED_PROXIES` (loopback defaults), scanning right to left; client IP controls rate limits, not user role. `APP_URL` is the public-origin reference. Optional `CLOUDFLARE_ACCESS_TEAM_DOMAIN` plus `CLOUDFLARE_ACCESS_AUD` (browser application) and `CLOUDFLARE_ACCESS_SERVICE_AUD` (service application for `/api/ingest` and `/api/agent` roots and descendants) verifies route-specific edge assertions on protected paths without deriving an application user. Deployment expectations are in [MCP deployment](../mcp.md#deployment), [configuration](../configuration.md), and [Cloudflare setup](../deploy/cloudflare.md): Access normally protects browser paths, while discovery, registration, token and MCP bypass browser challenges; service callers may also need Access service credentials. **Actual deployed Access, tunnel ingress, proxy ACLs, cache policy and network reachability were not verified**. Application authorization must stand independently.

## Coverage and limits

- The tables enumerate all registered routes and their authentication, role and object guards. The anonymous HTTP matrix covers 165 private literal registrations using anonymous, forged-edge and invalid-credential requests. GET/DELETE MCP intentionally answer 405.
- Scope is application and release-image hardening. Compose/runtime hardening belongs to PR #104; repository ignore/workflow/seed-domain changes belong to PR #103.
- Public CORS applies only to bearer/discovery endpoints and never allows credentials. Cookie writes check the configured public origin; HTTPS cookies use Secure, HttpOnly, SameSite=Lax and the host-only prefix. HTML has hashed-script CSP; non-HTML responses deny scripts/framing; HTTPS enables HSTS, nosniff and same-origin referrers.
- Upload paths already enforce size and allowed media types, including multipart overhead and bounded CSV imports. Luma links resolve through the fixed provider client, Drive uses fixed Google API/token hosts (ignoring a service-account token_uri), Discord uses configured provider endpoints, and Notion is a stub. No user-controlled URL is fetched as a general proxy.
- Drive receipt URLs are returned only after requester/director authorization. The service account requests full Drive scope; uploads inherit parent shared-drive ACLs and do not create an anyone-with-link permission. Actual Drive files/folder membership and independently shared links were not inspected. D9 limits this to exposure review; no ACL or scope changes were made.
- Access agent bypasses in the deployment guide match discovery, registration, token and MCP endpoints. Discovery/registration return no officer records; token exchanges require OAuth credentials; every MCP tool re-enters the API authorization layer. Optional JWT verification additionally exempts health for container probes; invite previews and consent stay behind Access when enabled. Actual deployed ingress, Access policy and provider ACLs remain unverified.
- Service tokens are stored as SHA-256 digests and looked up by digest; there is no plaintext token equality comparison. Scopes, expiry, revocation and active director creator are checked. OAuth grants enforce resource/audience, expiry, active user, revocation, PKCE, one-time codes and rotating refresh-token replay detection.
- Base-image builder tags remain mutable (low); the final BusyBox manifest is digest-pinned. Shared authenticated read APIs do not have a general search/read quota (low). Operational tuning and live provider checks remain separate follow-up work.
- Verification results and exact image/commit identifiers are recorded in the PR and private status report. Local synthetic tests do not certify the deployed service or external provider ACLs.
